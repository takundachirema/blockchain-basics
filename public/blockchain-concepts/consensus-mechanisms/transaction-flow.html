Transaction Flow

Transaction Validation Flow

The diagram below shows the end-to-end flow of how transactions move from users to finalized ledger updates.

Transaction validation flow: From signed transactions to verified blocks and updated ledger state.

  1. Senders create and sign transactions: Users form transactions and sign them with their private keys. These signed payloads are broadcast as proposed transactions and enter the network transaction pool.
  2. Miners/validators select transactions for a block: A block producer selects transactions from the pool and builds a candidate block. Block capacity limits throughput (TPS). For example, Bitcoin blocks have historically been constrained around ~1 MB, which contributes to low base-layer TPS and longer confirmation latency. Larger blocks can include more transactions, but they also increase propagation demands and can raise fork/orphan risk if peers cannot relay blocks quickly enough.
  3. Block broadcast and network verification: The candidate block is broadcast to peers, and nodes independently verify signatures, balances/UTXOs, nonces/order rules, and consensus requirements. Decentralization matters because concentrated control can enable censorship or majority attacks. In PoW contexts, if one coordinated entity controls a majority of effective hashing power (commonly discussed as 51%+), they can more easily reorganize recent history.

    In PoW mining, miners vary the nonce (and sometimes extra block fields) to search for a valid block hash that satisfies the difficulty target (conceptually, a hash below a threshold, often simplified as "starting with enough zeros"). On Bitcoin, mining difficulty is retargeted roughly every 2016 blocks (about two weeks) to keep average block intervals near 10 minutes.
  4. Valid blocks are accepted and appended: If the proposed block passes validation, nodes add it to their local ledger copy and continue building on it.
  5. Transactions approach finality: In PoW, finality is probabilistic and strengthens with confirmations under the longest-chain rule (e.g., Bitcoin often uses ~6 confirmations as a common safety threshold). In PoS systems, finality is reached through validator voting/attestation rules; in Ethereum PoS, committees are assigned with proposers and attesters, and finalized checkpoints provide stronger settlement guarantees.

Transaction Blocks

Transactions in a blockchain are grouped together into blocks. Each block contains:

  • A set of transactions
  • A reference to the previous block (creating a chain)
  • Proof of the consensus mechanism (e.g., proof of work solution)
  • Metadata about the block

Validating Transactions

Before a transaction is included in a block, it must be validated. Validators check:

Two checks happen:
  • Check 1: Transaction inclusion in a block (membership proof)
  • Check 2: Transaction validity (rules and signatures)

Check 1: Inclusion via Merkle Tree and Merkle Root

Inclusion asks: Is this transaction actually part of this block? Nodes and light clients can verify this using a Merkle proof. The transaction hash is combined with sibling hashes up the tree until it reconstructs the block’s Merkle root. If the reconstructed root matches the root stored in the block header, inclusion is proven.

Merkle proof idea: A transaction is included if its hash path recomputes the Merkle root in the block header.

Check 2: Transaction Validity

Validity asks: Even if included, is the transaction allowed by protocol rules? This includes signature correctness, sufficient balance/UTXO availability, nonce/order correctness, and proper transaction format.

  • Signature: The transaction is properly signed with the sender's private key
  • Balance: The sender has sufficient funds
  • Nonce: The transaction nonce is correct (prevents replay attacks)
  • Format: The transaction follows the correct format
  • Gas: Sufficient gas is provided for execution
Block Validation: Once a block is proposed, other nodes validate:
  • All transactions in the block are valid
  • The block follows consensus rules
  • The proof (PoW solution or PoS signature) is valid
  • The block links correctly to the previous block

Transaction Finality and the Longest Chain Rule

Transaction finality refers to the point at which a transaction is considered irreversible and permanently part of the ledger. In a distributed network, different nodes may sometimes produce valid blocks at nearly the same time, creating a temporary fork: two competing branches of the chain. The network must agree on which branch is the canonical one. This is where the longest chain rule applies.

Under the longest chain rule, when two valid blocks are found and broadcast at the same time, the tie is broken when the next block is found. That next block is built on top of one of the two competing blocks. The branch that gets extended becomes the accepted chain; the other branch's tip is treated as an orphan block and is no longer part of the canonical chain. Nodes therefore consider the longest (most cumulative proof-of-work or, in Proof of Stake, the chain with the most attestations) as the true history.

The deeper a transaction is buried under subsequent blocks, the more confident we can be that it has achieved finality, because reverting it would require replacing a longer chain. In practice, services often wait for a certain number of confirmations (blocks built on top of the block containing the transaction) before treating a transfer as final.

How finality is achieved depends on the consensus mechanism:

  • Probabilistic Finality (PoW): Blocks become more final as more blocks are added on top. Generally, 6+ confirmations provide strong confidence.
  • Deterministic Finality (PoS): Blocks are finalized after a certain number of epochs through a voting process. Once finalized, they cannot be reversed except through extreme circumstances.

Longest chain rule: When two valid blocks are broadcast at the same time (TIE), the next block that is found is built on one branch. That branch becomes the canonical chain; the other branch's tip is the orphan block (TIE IS BROKEN).
